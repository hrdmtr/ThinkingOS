# Thinking OS（仮称）開発ルール

## ブランチ戦略：GitHub Flow

`develop`ブランチ・`hotfix`ブランチは作らない。ブランチは常に2種類だけ。

- **`main`**：常にデプロイ可能な状態を保つ。
- **作業ブランチ**：機能追加・バグ修正を問わず、`main`から切る。命名は内容が分かればよい（例：`feature/xxx`、`fix/xxx`）。フローの種類は変わらないので、接頭辞は分類目的のみ。

## 基本の流れ

1. `main`から作業ブランチを切る
2. 作業ブランチで変更する
3. `main`へのPRを作成する
4. マージする
5. マージ後、すぐデプロイする

機能追加もバグ修正も、この同じ流れで扱う。ブランチの起点を作業内容によって使い分けない（Git Flowのdevelop/hotfixのような分岐はしない）。

## この方針を選んだ理由

- 開発者一人のn=1プロジェクトで、複数バージョンを並行運用する必要がない
- ドッグフーディングは短いサイクルで素早く直しながら進める前提のため、`main`に入ったらすぐ使える状態を保つのが合っている
- ブランチの種類を減らすことで、「今回はどこから切るべきか」を毎回判断するコストと、判断を誤るリスクを減らす
