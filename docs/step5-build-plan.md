# Thinking OS（仮称）Step 5｜構築計画・要件定義

> Step 5成果物。企画書（`thinking-os-plan-v0.2.docx`）セクション6・8の方針を、実装に落とせる粒度まで具体化したもの。

---

## 1. ノード抽出パイプラインの実装方式

**バッチ処理（会話セッション終了後）を採用する。**

- 会話セッションの終了（明示的な終了操作、または一定時間の無操作）をトリガーに、そのセッションの会話ログ全体をまとめてAIに渡し、アイデア／仮説／根拠／判断／未解決事項／タスクを抽出する。
- リアルタイム処理（発言ごとに都度推論）は、実装の複雑さとレイテンシがUXに影響するリスクがあるため見送る。将来的にMVPの手応えを見てから検討する。
- 抽出結果・関連候補は、セッション終了直後（バッチ処理が返ってきた数秒後）にその場で提示する。次回起動を待たせない（3章参照）。「今日の問い」「最近更新された知識」画面には、確定済みのデータが以降も表示され続ける。会話中に即座に関連候補が出る体験は持たない（v0.1で優先度が後退した「毎朝ひとこと話しかける」機能とは別軸の割り切り）。

## 2. データ永続化方式

企画書セクション8の方針（グラフDBは導入せず、軽量な構造から始める）を踏まえ、以下を最小構成とする。

- **保存先**：ローカルのSQLiteを1ファイルDBとして使う（軽量・単一ユーザー・後からの移行が容易という理由。特定の言語・フレームワークへの依存はここでは規定しない）。
- **nodesテーブル**：`id`, `type`（アイデア／仮説／根拠／判断／未解決事項／タスク）, `content`, `created_at`, `session_id`。単一テーブルとし、typeごとにテーブルを分けない（企画書セクション8の方針通り）。エッジと同じ考え方で、AIが抽出した直後の候補はDBに書き込まず、ユーザーが3章の統合レビュー画面で確定した時点で初めてINSERTする（未確定候補の永続化はしない。ステータス列は不要）。
- **edgesテーブル**：`id`, `source_node_id`, `target_node_id`, `label`, `strength`（任意）, `discovered_at`。AIが提示した関係候補は、ユーザーが確定した時点で初めてこのテーブルに書き込む。AIが提示しただけの未確定候補は永続化しない（毎回のバッチ処理で再提示されればよいため）。
- **エッジラベルの語彙**：初期候補「対比」「帰結」「想起」を自由入力可能なテキストカラムとして持たせ、固定リストへの強制はしない（この決定を企画書本体セクション8に反映済み。旧セクション11にあった当該の未解決論点は解消済みとして削除した）。

## 3. セッション終了直後の統合レビュー画面（AI提案→ユーザー確定のフロー）の最小設計

ノードとエッジを別画面・別タイミングにせず、セッション終了直後の1画面にまとめてレビューする。当初案では「エッジ候補のみ確認し、ノードは無審査で保存」という非対称な設計だったが、これは「AIは提案まで、確定は人間」という原則にノードだけ反する形になるため見直した。

- **タイミング**：「壁打ちを終える」操作の直後、バッチ抽出APIが返ってきたその場で表示する（1章参照）。次回起動まで待たせない。
- **構成**：抽出されたノード候補を、type別（アイデア／仮説／根拠／判断／未解決事項／タスク）にグループ化して一覧表示する。あわせて、それらノード間の関係候補（AIが提示したラベル案付き）も同じ画面に表示する。
- **ユーザーの操作**：ノード・エッジのどちらも同じ3択。
  1. **確定**：提示された内容のまま確定 → nodes／edgesテーブルに保存
  2. **修正**：内容やラベルを書き換えてから確定 → 書き換えた内容で保存
  3. **却下**：不要として破棄 → 何も保存しない（AIは次回また候補を作り直してよい。却下履歴の学習はMVP対象外）
  - 個別に確認する以外に、「これで全部OK」という一括確定の操作も用意し、レビューの手間を減らす（type別グループ表示は一括確認のしやすさのため）。
- 「聞き返し」（企画書セクション7）は、確定・修正いずれの操作の際にも、ユーザーが望めば「なぜこう分類・提示したのか」をAIに尋ねられる導線を用意する（常時表示のラベルや根拠表示は行わない）。
- 却下・未確定のノード・エッジはDBに保存しない（2章参照）。統計（5章）は確定済みのものだけを数える。

## 4. 「毎朝ひとこと話しかける」機能の要否・優先度

**MVP対象外とし、将来機能に位置づける。**

- 企画書v0.1では中心機能候補だったが、v0.2の議論でノード・エッジの永続化パイプラインより優先度を下げる方針が確定済み（企画書セクション6・10）。
- MVP成功基準は「壁打ちからの新規着想」「整理速度」を命題数で測ることであり、これはユーザー起点の壁打ちセッションがあって初めて計測できる。プッシュ型の声かけ機能がなくても指標は測定可能なため、MVPの必須要件ではないと判断する。
- 将来機能としては維持し、ドッグフーディングの結果次第で優先度を再評価する。

## 5. 統計表示（セッション単位・累計）

企画書v0.2の改訂（セクション6）およびStep 4（`docs/step4-dogfooding.md`）を踏まえ、MVPの表示要素に以下を追加する。比較対象となる既存製品がないため、他製品比の速度倍率のような相対指標ではなく、絶対的な統計そのものを画面に表示する。

- セッション終了時：「今回の壁打ちで生まれた命題：N件」を表示
- 常設表示（「最近更新された知識」等と並べて）：「これまでに整理した命題：NN件、作成した関係：MM件」
- これらはnodes／edgesテーブルの件数をそのまま集計すればよく、追加の分析処理は不要。

## 6. プラットフォーム（配信形態）

**SPA（Webアプリ）を採用する。必要に応じてPWA化し、スマホのホーム画面に追加できるようにする。**

- ネイティブスマホアプリは見送る。ネイティブが主に必要になる理由（プッシュ通知、オフライン利用）は、いずれもMVP対象外（4章の「毎朝ひとこと話しかける」機能）または現段階で不要なため、採用する動機がない。
- ドッグフーディングは4週間サイクルで素早く手直ししながら進める前提（`docs/step4-dogfooding.md`）のため、ストア審査を挟むネイティブアプリは足かせになる。単一コードベースのSPAなら、更新をデプロイするだけでPC・スマホ両方のブラウザに即反映できる。
- SQLiteをバックエンドに置く軽量構成（2章）と相性がよく、当面はサーバー1台・DBファイル1つのシンプルな構成で運用できる。
- ネイティブアプリ化は、n=1検証を終え、プッシュ通知等の常時携帯性が本当に必要だと判明してから検討する将来オプションとする（企画書セクション10「将来機能」の考え方と整合）。
